Hackatón hexagonal

En equipo y contra el reloj: convierten la API de notas en una arquitectura hexagonal —dominio, puertos y adaptadores— y la empacan en un contenedor. Un verificador comprueba cada etapa, y un marcador en vivo suma los puntos.

El caso: Notas del semestre

Es el mismo caso del ejercicio de APIs. Cada estudiante registra las evaluaciones del semestre (nombre, peso y nota) y quiere saber cuánto lleva acumulado. Hoy lo hace en una hoja de cálculo donde los pesos suman 120 %, aparece una nota de 7 y se repiten nombres. Se pide una API que cuide las reglas: hoy la usa una web; mañana, una app y un bot; hoy guarda en memoria o en un archivo, mañana en una base de datos. Las reglas no pueden cambiar según quién pregunte ni según dónde se guarde. De eso trata el hackatón.

ReglaEl dominio avisa conHTTP
El nombre es obligatorio (hasta 40 caracteres)NOMBRE_INVALIDO422
El peso es un entero entre 1 y 100PESO_INVALIDO422
La nota va de 0 a 5NOTA_INVALIDA422
El nombre no se repiteNOMBRE_REPETIDO409
Los pesos juntos no pasan de 100PESO_EXCEDIDO409
La evaluación tiene que existirNO_EXISTE404

El acumulado es la suma de peso ÷ 100 × nota de las evaluaciones ya calificadas. Ejemplo: Parcial 1 (30 %, nota 4.5) y Taller (20 %, nota 3.8) dan 1.35 + 0.76 = 2.11, con el 50 % del semestre calificado.

Qué se juega aquí

El dominio (ya escrito en src/dominio/evaluacion.js) decide qué regla se rompió y avisa con un código; no sabe nada de HTTP ni de archivos. El caso de uso (etapa 1) le da lo que necesita, como la lista de lo ya guardado, porque el dominio no puede ir a buscarla. El adaptador HTTP (etapa 3) decide cómo contarlo: 422, 409 o 404. El adaptador de salida (etapa 2) guarda donde toque. Ustedes construyen todo lo que rodea al dominio, y después lo ven funcionar capa por capa.

Las reglas del juego

Cinco reglas

1. Equipos de 3 (mínimo 2) y un repositorio público por equipo, creado desde la plantilla. 2. Cada etapa tiene un verificador: npm run verificar. Lo que pasa queda anotado en progreso.json, con la hora de la primera vez que pasó. 3. Con git push el marcador lo lee de su repositorio. Suman los puntos de la etapa y 3, 2 y 1 más para quienes la completen primero, segundo y tercero. 4. Gana quien tenga más puntos al terminar; si hay empate, quien llegó antes a su última etapa. 5. Juego limpio: el docente puede repetir el verificador en cualquier repositorio (un resultado que no se reproduce no cuenta); se vale ayudarse entre equipos, no copiar código; y cada integrante debe poder explicar el código de su equipo. El docente dirá si se pueden usar asistentes de IA.

Premios simbólicos (los define el docente): primer, segundo y tercer lugar por puntos · primera sangre, para el primer equipo que complete cualquier etapa · doble motor, para quien complete la imagen con Docker y con Podman.

Antes de empezar

  • Node.js 22 o superior. Comprueben con node -v. No hay que instalar paquetes: el proyecto no tiene dependencias.
  • Git y una cuenta de GitHub por integrante. Una persona crea el repositorio del equipo (público) y agrega a las demás.
  • Un motor de contenedores: Docker o Podman (o los dos). Es la Etapa 0 y la descarga es grande: empiécenla ya, mientras el docente explica. Sigan las instrucciones de instalación de la documentación oficial de su sistema (cambian con el tiempo): Docker Desktop o Docker Engine; Podman o Podman Desktop. En macOS y Windows, Podman necesita su máquina virtual: podman machine init y podman machine start.
  • Un editor (VS Code recomendado) y una terminal.

Empiecen así

  1. Una persona abre la plantilla, pulsa Create repository from template, lo crea público con el nombre hackaton-su-equipo y agrega a las demás. Todas clonan: git clone https://github.com/USUARIO/hackaton-su-equipo.git.
  2. Abran equipo.json y escriban el nombre del equipo y los integrantes. Sin nombre, el marcador no sabrá quiénes son.
  3. Corran el verificador y vean el punto de partida: 
    cd hackaton-su-equipo
npm run verificar -- 1 2 3 4
    Todo falla con un mensaje «TODO etapa N»: ahí empieza el juego.
  4. Repártanse el trabajo. Las etapas 1, 2 y 3 son independientes (cada una se prueba con piezas falsas de las otras): una persona puede instalar el motor de contenedores y adelantar el Dockerfile mientras las otras dos hacen los casos de uso y los adaptadores. La composición (4) y la imagen (5) las arman juntas.
  5. Cuando una etapa pase: git add -A && git commit -m "Etapa 1" && git push. Verán su fila en el marcador en unos minutos (GitHub guarda cada archivo hasta 5).

Etapa 0 · Contenedor listo

10 puntos

Un motor de contenedores instalado, corriendo y capaz de ejecutar un contenedor.

  1. Instalen Docker o Podman (ver «Antes de empezar») y arránquenlo: Docker Desktop abierto y diciendo que el motor está corriendo; Podman con su máquina virtual iniciada en macOS y Windows.
  2. Comprueben: docker --version o podman --version, y después npm run verificar -- 0. El verificador ejecuta hello-world, que se descarga de internet la primera vez.
Si no pasa
  • «está instalado pero no responde»: el programa existe, pero el motor no está arrancado. Ábranlo y esperen a que termine de iniciar; en Podman (macOS y Windows) corran podman machine start.
  • Tarda o falla la descarga: hello-world se baja de internet; ¿hay conexión? Con una red lenta, pueden tardar unos minutos.
  • Tienen los dos motores: perfecto, el verificador usa el primero que responda. Más adelante hay un extra por usar los dos.

Etapa 1 · Casos de uso

15 puntos

Archivo: src/aplicacion/casos-de-uso.js. Un caso de uso orquesta: pide datos al puerto de salida (el repositorio), le pide al dominio que decida y guarda. No sabe si el repositorio es memoria, archivo o base de datos.

  1. Lean src/dominio/evaluacion.js y src/aplicacion/puerto-repositorio.js: las reglas y el acuerdo.
  2. Implementen los seis métodos de crearCasosDeUso({ repositorio }): listar, ver, crear, calificar, eliminar y resumen. Las reglas las pone el dominio: no las copien.
  3. Comprueben: npm run verificar -- 1. Las pruebas usan un repositorio falso de 10 líneas: no necesitan HTTP ni archivos.
Pistas (ábranla solo si llevan más de 10 minutos atascados)
  • crear: Evaluacion.crear(datos, repositorio.listar()) valida con lo que ya existe; después repositorio.guardar(...) y devuelven lo que él devuelva (trae el id).
  • Tres métodos necesitan «buscar o fallar»: escriban una función pequeña buscar(id) que use repositorio.obtener(id) y, si no hay nada, lance new ErrorDeDominio(CODIGOS.NO_EXISTE, '…').
  • calificar: buscar → Evaluacion.calificar(encontrada, nota) → guardar. eliminar: buscar (para que falle si no existe) → repositorio.eliminar(id).
  • El archivo ya importa lo que necesita del dominio; no importen nada más (la etapa 4 y esta prueba lo vigilan).

Etapa 2 · Adaptadores de salida

15 puntos

Archivos: src/adaptadores/salida/repositorio-memoria.js y repositorio-archivo.js. Dos adaptadores que cumplen el mismo puerto: las mismas pruebas de contrato los comprueban a los dos.

  1. Relean el contrato en puerto-repositorio.js: los cuatro métodos, el id «mayor + 1», las copias y que son síncronos.
  2. Escriban el de memoria (un arreglo) y el de archivo (un arreglo JSON en disco, con readFileSync y writeFileSync).
  3. Comprueben: npm run verificar -- 2. Si el de archivo pasa las mismas pruebas que el de memoria, son intercambiables: esa es la gracia.
Pistas (ábranla solo si llevan más de 10 minutos atascados)
  • Copias: devuelvan { ...evaluacion }, no el objeto que guardan. Si no, quien modifique lo recibido cambia el repositorio sin querer.
  • Id nuevo: el mayor id que exista más 1 (el primero es 1): lista.reduce((mayor, e) => Math.max(mayor, e.id), 0) + 1.
  • Archivo: una función leer() (devuelve [] si el archivo no existe: existsSync) y una escribir(lista). Antes de escribir, creen la carpeta: mkdirSync(dirname(ruta), { recursive: true }).
  • Reemplazar: si guardar recibe un id que ya existe, reemplaza esa evaluación (no la duplica).

Etapa 3 · La API HTTP

20 puntos

Archivo: src/adaptadores/entrada/http.js. La API es un adaptador más: traduce HTTP al idioma del negocio y viceversa. Las rutas traducen, no deciden: la prueba lo comprueba.

  1. Lean nucleo-http.mjs (arriba del todo): qué recibe y qué devuelve un manejador. Las rutas llevan llaves: /evaluaciones/{id}.
  2. Completen crearRutas(casos) con las seis rutas que lista el archivo (y sus estados: 200, 201 con Location, 204), y la tabla ESTADO_POR_CODIGO con traducirError.
  3. Comprueben: npm run verificar -- 3. La prueba usa casos de uso falsos: no depende de las etapas 1 y 2.
Pistas (ábranla solo si llevan más de 10 minutos atascados)
  • El id llega como texto ("3"): conviértanlo con Number(params.id) antes de llamar al caso de uso.
  • Estados: lo que no existe, 404. Un valor inválido (nombre, peso o nota), 422. Un choque con el estado actual (nombre repetido, pesos que pasan de 100), 409. Es lo mismo que decidieron en la clase de APIs.
  • Crear: { status: 201, cuerpo: creada, cabeceras: { Location: '/evaluaciones/' + creada.id } }. Eliminar: { status: 204 }, sin cuerpo.
  • Calificar: el cuerpo es { "nota": 4.5 }; pasen cuerpo.nota al caso de uso.
  • No validen en la ruta. Si descubren un if (peso > 100) en http.js, bórrenlo: ya lo hace el dominio.

Etapa 4 · Composición

15 puntos

Archivo: src/configuracion.mjs. El único lugar que conoce todas las piezas: elige el adaptador de salida según una variable de entorno, construye los casos de uso y la API.

  1. Implementen componer(entorno): ALMACEN (memoria por defecto, o archivo), DATOS (la ruta del archivo; por defecto datos/evaluaciones.json) y PORT (por defecto 3000, como número). Un ALMACEN desconocido es un error claro que menciona ALMACEN.
  2. Prueben a mano: npm start y, en otra terminal, curl http://localhost:3000/salud. Después ALMACEN=archivo npm start, creen algo, reinicien y comprueben que sigue ahí.
  3. Comprueben: npm run verificar -- 4. Además de que funcione, esta etapa vigila la regla de dependencias: nada de src/dominio ni de src/aplicacion puede importar módulos de Node (node:fs, node:http…), adaptadores ni la configuración.
Pistas
  • Es un if / else if / else que construye repositorio; después crearCasosDeUso({ repositorio }) y crearApi(casos). Devuelvan { servidor, puerto, almacen }.
  • Para probar a mano en Windows PowerShell: $env:ALMACEN = "archivo"; npm start.
  • Si la regla de dependencias falla, el mensaje dice qué archivo importa qué. Casi siempre es un import ... from 'node:...' que se coló en el dominio o en un caso de uso.

Etapa 5 · Imagen

25 puntos

Creen un Dockerfile (o Containerfile) en la raíz: una imagen con su API. El verificador la construye, arranca un contenedor, espera a que /salud responda y usa la API de verdad (crear y listar).

  1. Escriban el archivo. Una imagen se arma en capas: de qué imagen parte (FROM), dónde trabaja (WORKDIR), qué copia (COPY), qué variables fija (ENV) y qué ejecuta (CMD).
  2. Pruébenla a mano antes de verificar: 
    docker build -t notas-hex .
docker run -d --name notas -p 3000:3000 notas-hex
curl http://localhost:3000/salud
docker rm -f notas
    Con Podman es lo mismo cambiando docker por podman.
  3. Comprueben: npm run verificar -- 5.
Pistas (ábranla solo si llevan más de 10 minutos atascados)
  • Imagen de partida: Node 22. Escríbanla completa: docker.io/library/node:22-alpine (la versión «alpine» es pequeña). Con Podman conviene el nombre completo: así no tiene que elegir de qué registro bajarla.
  • Qué copiar: package.json y la carpeta src. El proyecto no tiene dependencias, así que no hace falta npm install. El archivo .dockerignore ya viene hecho.
  • Cómo arranca: CMD ["node", "src/main.mjs"]. El servidor ya escucha en 0.0.0.0 y lee PORT: fijen ENV PORT=3000 y EXPOSE 3000.
  • «No responde en /salud»: ¿publicaron el puerto (-p 3000:3000)? ¿La aplicación escucha en 0.0.0.0? Miren el registro: docker logs notas.

Miren cómo viaja una petición

Cuando tengan hechas las etapas 1, 2 y 3 (la 4 y la 5 no hacen falta), corran:

node recorrido.mjs

El archivo arma la API con su código, manda cinco peticiones de verdad y escribe, línea por línea, quién llamó a quién: la ruta HTTP, el caso de uso, el puerto con su adaptador de almacenamiento, y el dominio decidiendo. Al final repite todo con el otro almacén (memoria y archivo) y compara. No da puntos: sirve para ver la arquitectura que construyeron.

Si su repositorio se creó antes de que existiera este archivo, bájenlo a la raíz del proyecto:

curl -O https://raw.githubusercontent.com/xaviercardona-ops/hackaton-hexagonal/HEAD/recorrido.mjs

En PowerShell: Invoke-WebRequest https://raw.githubusercontent.com/xaviercardona-ops/hackaton-hexagonal/HEAD/recorrido.mjs -OutFile recorrido.mjs. O cópienlo desde el repositorio de la plantilla.

Para pensar (y para contárselo al equipo)
  • En la petición 2, ¿quién decidió que el peso 0 no vale: la ruta, el caso de uso o el dominio? ¿Quién lo convirtió en 422?
  • Si mañana el almacén fuera una base de datos, ¿qué archivos tocarían? ¿Cuáles no?
  • ¿Qué pasaría si src/dominio/evaluacion.js importara node:fs? ¿Qué etapa lo detectaría?
  • El caso de uso llamó al almacén, pero en su código no importa ningún adaptador. ¿Cómo le llegó el repositorio? (Pista: etapa 4.)

Vocabulario

TérminoQué quiere decir aquí
DominioLas reglas del negocio, sin saber nada de HTTP, archivos ni bases de datos.
Caso de usoUna cosa que el negocio ofrece (crear una evaluación). Orquesta el dominio y los puertos.
PuertoUn acuerdo entre el centro y lo de afuera. De entrada (qué ofrece el negocio) o de salida (qué necesita).
AdaptadorEl código que cumple un puerto con una tecnología concreta: la API HTTP, el repositorio de archivo.
ComposiciónEl único lugar que conoce todas las piezas y las conecta (aquí, configuracion.mjs).
Prueba de contratoLas mismas pruebas ejecutadas contra todos los adaptadores de un puerto.
Imagen / contenedorLa imagen es la receta empacada (la aplicación y lo que necesita); el contenedor es esa imagen en ejecución.
VolumenUn lugar de almacenamiento que vive fuera del contenedor, para que los datos sobrevivan cuando se destruye.
Motor de contenedoresEl programa que construye imágenes y corre contenedores: Docker o Podman.
